# File format facts for the VTClassic UTL format.

## Format

### Traps / known differences from JS
- [Verified] `CountedStreamWriter` counts UTF-16 code units via `string.Length`. `string.Length`. Same as JS `string.length`. See: `ref/shared/CountedStreamWriter.cs`
- [Verified] .NET Framework writes a double as "G15": 15 significant digits, then trailing zeros removed. Scientific notation (`1E-05`, `1.5E+20`) when the exponent is below -4 or 15 and above. Test: `src/core/format/doubles.test.ts`, "against .NET G15 output" (values from a real `dotnet run`).
- [Verified] JS `String(x)` differs from .NET even for normal values: `1/3` gives `0.3333333333333333` in JS and `0.333333333333333` in .NET. Test: same file.
- [Verified] `CountedStreamWriter.Write(double)` uses `Convert.ToString(x, InvariantCulture)`. C# `Write(double)` uses `Convert.ToString`. See: `ref/shared/CountedStreamWriter.cs`

### Profile and rule records
- [Observed] A version 0 file starts with the rule count. A version 1 file starts with `UTL`, the version number, then the rule count. `ref/shared/LootRules.cs:3140-3155`.
- [Observed] A version 1 file prefixes each requirement body with its character count. A version 0 file has no prefix. `ref/shared/LootRules.cs:2976-2999`.
- [Observed] An unknown requirement is skipped by its count and kept as raw characters. `ref/shared/LootRules.cs:2987-2992`.
- [Observed] The writer always saves version `MAX_PROFILE_VERSION` (1), whatever the input version was. `ref/shared/LootRules.cs:3181`.
- [Verified] `readProfile` then `writeProfile` gives the same bytes for `vtclassic_editor_minimal.utl`, `vtclassic_editor_rich.utl`, `BuffedLongBuffedDouble.utl` and `UnfamilarShores.utl` with types 0 and 1 parsed and the other types still raw. Test: `src/core/format/profile.test.ts`.

### Requirement types
- [Observed] Type 0 `SpellNameMatch` reads one line as the regex pattern (`inf.ReadLine()`) and writes it back as one line. The pattern stays text. `ref/shared/LootRules.cs:313,318`.
- [Observed] Type 1 `StringValueMatch` reads two lines. The first line is the pattern. The second line is the `StringValueKey` number (`Convert.ToInt32`). It writes them back with `Convert.ToString((int)vk, InvariantCulture)`, so the key is base 10. `ref/shared/LootRules.cs:379-386`.
- [Verified] A type 0 body is `pattern + CRLF`. A type 1 body is `pattern + CRLF + key + CRLF`. Both bodies round-trip through their length prefix. Test: `src/core/format/profile.test.ts`, "requirement type 0, SpellNameMatch" and "requirement type 1, StringValueMatch".
- [Observed] Types 2 (`LongValKeyLE`), 3 (`LongValKeyGE`), 11 (`LongValKeyFlagExists`), 12 (`LongValKeyE`) and 13 (`LongValKeyNE`) all read two lines: `keyval` as `Convert.ToInt32`, then `vk` as `Convert.ToUInt32` cast to `IntValueKey`. They write the same two lines with `Convert.ToString(..., InvariantCulture)`, so both are base 10. `ref/shared/LootRules.cs:454-461,571-578,1187-1194,1412-1419,1529-1536`.
- [Verified] A type 2, 3, 11, 12 or 13 body is `keyval + CRLF + vk + CRLF`. All five types round-trip through their length prefix, a negative keyval keeps its sign, and the real examples in `IAC_Level_NoCash.utl` parse to `{keyval, vk}` pairs. Test: `src/core/format/profile.test.ts`, "requirement type 2, LongValKeyLE" through "requirement type 13, LongValKeyNE".
- [Verified] `readProfile` then `writeProfile` gives the same bytes for all 8 fixtures, including the three whose writer is unknown (`BuffedLongBuffedDouble.utl`, `vtclassic_editor_minimal.utl`, `vtclassic_editor_rich.utl`). No requirement in any fixture stays unsupported. Test: `src/core/fixtures.test.ts`, "fixture round-trip".
- [Observed] Types 4 (`DoubleValKeyLE`) and 5 (`DoubleValKeyGE`) read `keyval` with `GameInfo.HaxConvertDouble`, then `vk` as `Convert.ToUInt32` cast to `DoubleValueKey`. Types 6 (`DamagePercentGE`) and 10 (`MinDamageGE`) read only the `keyval` line. All four write `keyval` with `Convert.ToString(keyval, InvariantCulture)`. `ref/shared/LootRules.cs:686-696,761-771,827-835,1119-1127`.
- [Observed] `HaxConvertDouble` changes `,` to `.`, then calls `double.TryParse` with `NumberStyles.Float` and `InvariantCulture`. It returns 0 when the parse fails. `ref/shared/Constants.cs:415-422`.
- [Verified] A type 4 or 5 body is `formatDouble(keyval) + CRLF + vk + CRLF`. A type 6 or 10 body is `formatDouble(keyval) + CRLF`. A comma reads as the decimal point, and bad text reads as 0. The real type 4 and 5 examples in `LootSnobV4.utl` parse. No fixture has type 6 or 10. Test: `src/core/format/profile.test.ts`, "requirement types 4 and 5" and "requirement types 6 and 10", and `doubles.test.ts`, "haxConvertDouble".
- [Observed] Type 7 `ObjectClassE` reads one line as `Convert.ToUInt32` and casts it to `ObjectClass`. It writes one line as `Convert.ToString((int)vk, InvariantCulture)`, so the value is base 10. `ref/shared/LootRules.cs:891,893`.
- [Observed] Type 8 `SpellCountGE` reads one `Convert.ToInt32` line and writes it with `Convert.ToString(..., InvariantCulture)`. `ref/shared/LootRules.cs:957,959`.
- [Observed] Type 9 `SpellMatch` reads and writes three lines: the `rxDoesMatch` regex, the `rxDoesNotMatch` regex, then `Count` as `Convert.ToInt32`. Both regexes stay text. `ref/shared/LootRules.cs:1043-1046`.
- [Verified] A type 7 body is `vk + CRLF`, and a type 8 body is `keyval + CRLF`. A type 9 body is `rxDoesMatch + CRLF + rxDoesNotMatch + CRLF + count + CRLF`. All three round-trip through their length prefix, and a negative type 8 keyval keeps its sign. An empty type 9 "does not match" pattern stays an empty line. The real type 7 example in `UnfamilarShores.utl` and the real type 9 example in `vtclassic_editor_rich.utl` parse, and no fixture has type 8. Test: `src/core/format/profile.test.ts`, "requirement type 7, ObjectClass" through "requirement type 9, SpellMatch".
- [Observed] Type 1000 `CharacterSkillGE` reads two lines: `keyval` as `Convert.ToInt32`, then `vk` as `Convert.ToUInt32` cast to `VTCSkillID`. It writes both with `Convert.ToString(..., InvariantCulture)`, so both are base 10. `ref/shared/LootRules.cs:1264-1273`.
- [Observed] Types 1001 `CharacterMainPackEmptySlotsGE`, 1002 `CharacterLevelGE` and 1003 `CharacterLevelLE` read and write one `Convert.ToInt32` `keyval` line. `ref/shared/LootRules.cs:1344-1351,1635-1642,1692-1699`.
- [Observed] Type 1004 `CharacterBaseSkill` reads and writes three lines: `vk` as `VTCSkillID`, then `minskill` and `maxskill` as `Convert.ToInt32`. All three are base 10. `ref/shared/LootRules.cs:1763-1774`.
- [Verified] A type 1000 body is `keyval + CRLF + vk + CRLF`, and a type 1001, 1002 or 1003 body is `keyval + CRLF`. A type 1004 body is `vk + CRLF + minskill + CRLF + maxskill + CRLF`. All five round-trip through their length prefix, and a negative keyval keeps its sign. The real type 1000 example in `ILT_Legendary.utl` (keyval 350, skill 23) and the real type 1001 example in `IAC_Level_NoCash.utl` (keyval 12) parse. No fixture has type 1002, 1003 or 1004. Test: `src/core/format/profile.test.ts`, "requirement type 1000, CharacterSkillGE" through "requirement type 1004, CharacterBaseSkill".
- [Observed] Type 9999 `DisabledRule` reads one line and keeps it true only when it is exactly `"true"` (`"true".Equals`, case-sensitive). It writes `b ? "true" : "false"`, so the body is always lowercase. `ref/shared/LootRules.cs:1839,1842-1844`.
- [Observed] Types 14 (`AnySimilarColor`), 15 (`SimilarColorArmorType`) and 16 (`SlotSimilarColor`) read five lines: `R`, `G`, `B` with `int.Parse`, then `MaxDifferenceH` and `MaxDifferenceSV` with `double.Parse(..., InvariantCulture)`, not `HaxConvertDouble`. Type 15 adds the `ArmorGroup` line, and type 16 adds the `Slot` line with `int.Parse`. The C# writes the doubles with `inf.WriteLine(double)` and no `InvariantCulture`, so the decimal point comes from the culture of the PC. The editor reads the doubles with `haxConvertDouble`, so a comma reads as the decimal point. `ref/shared/LootRules.cs:1934-1940,2083-2090,2239-2245`.
- [Observed] Type 17 `SlotExactPalette` reads and writes two lines: `Slot`, then `Palette`, both with `int.Parse`. `ref/shared/LootRules.cs:2326-2329`.
- [Verified] A type 9999 body is `"true\r\n"` or `"false\r\n"`. A type 14 body is `R + CRLF + G + CRLF + B + CRLF + maxDifferenceH + CRLF + maxDifferenceSV + CRLF`. A type 15 body adds the armor group line. A type 16 body adds the slot line. A type 17 body is `slot + CRLF + palette + CRLF`. Test: `src/core/format/profile.test.ts`, "requirement type 9999, DisabledRule" through "T12 types together".
- [Verified] Types 9999 and 14 to 17 all round-trip through their length prefix. Only lowercase `true` reads as true, and a negative type 17 slot keeps its sign. A comma reads as the decimal point in the type 14 differences. The real type 9999 examples (body `true`) of all 5 fixtures that have one parse to `b: true`. No fixture has type 14, 15, 16 or 17. Test: `src/core/format/profile.test.ts`, "requirement type 9999, DisabledRule" through "T12 types together".
- [Observed] Type 2000 `BuffedMedianDamageGE`, 2001 `BuffedMissileDamageGE`, 2006 `CalcdBuffedTinkedDamageGE` and 2007 `TotalRatingsGE` read one line with `GameInfo.HaxConvertDouble` and write it with `Convert.ToString(keyval, InvariantCulture)`. `ref/shared/LootRules.cs:2406-2408,2473-2475,2688-2690,2755-2757`.
- [Observed] Type 2003 `BuffedLongValKeyGE` and 2005 `BuffedDoubleValKeyGE` read two lines: `keyval` with `HaxConvertDouble`, then `vk` with `Convert.ToUInt32` cast to `IntValueKey` or `DoubleValueKey`. They write `keyval` with `Convert.ToString(..., InvariantCulture)` and `(int)vk` base 10. `ref/shared/LootRules.cs:2535-2538,2609-2612`.
- [Observed] Type 2008 `CalcedBuffedTinkedTargetMeleeGE` reads three lines with `double.Parse(..., InvariantCulture)` and writes them with `inf.WriteLine(double)` and no culture. `ref/shared/LootRules.cs:2821-2827`.
- [Verified] A type 2000, 2001, 2006 or 2007 body is `formatDouble(keyval) + CRLF`. A type 2003 or 2005 body is `formatDouble(keyval) + CRLF + vk + CRLF`. A type 2008 body is three double lines. All seven round-trip through their length prefix. Test: `src/core/format/profile.test.ts`, "requirement types 2000 and 2001" through "T13 types together".
- [Verified] The real type 2001 example in `LootSnobV4.utl` has keyval 78.6. The real type 2003, 2005 and 2007 examples in `BuffedLongBuffedDouble.utl` are 200/28, 20/167772172 and 300. The real type 2008 example in `ILT_Legendary.utl` is 109, 1.17, 1.17. No fixture has type 2000 or 2006. The reader uses `haxConvertDouble` for the type 2008 lines, as the types 14 to 16 readers do. Test: `src/core/format/profile.test.ts`, "requirement types 2000 and 2001" through "T13 types together".

### Extra blocks (T14)
- [Observed] An extra block after the rules has a type id line, a length line, then that many UTF-16 code units. A handler parses a known type id. Today `SalvageCombine` is the only known one. The reader skips an unknown type id and never re-writes it, so the C# editor drops that block on save. This editor keeps the raw body instead. `ref/shared/UTLFileExtraBlockManager.cs:44-70,94-137`.
- [Observed] A `SalvageCombine` body starts with the format version line. The reader ignores that line. It then reads the default combine string, the material count, and one material id and one combine string per material. It reads the value mode count and one material id and one target value per entry. The C# checks `inf.EndOfStream` on the whole file, so this works only when the block is last. `ref/shared/UTLBlock_SalvageCombine.cs:272-299`.
- [Observed] The `SalvageCombine` writer always saves format version 1. It always writes the value mode count, so an old block without a value mode section gains a `0` line on save. The .NET `Dictionary` writes the material ids in read order when nothing was removed. `ref/shared/UTLBlock_SalvageCombine.cs:302-321`.
- [Verified] A `SalvageCombine` body is `version + CRLF + default + CRLF + count + CRLF + (material + CRLF + combine + CRLF) * count + valueModeCount + CRLF + (material + CRLF + value + CRLF) * valueModeCount`. Test: `src/core/format/profile.test.ts`, "writes a literal block and reads it back".
- [Verified] The material order of a block is not sorted by id. The 25 ids of `BuffedLongBuffedDouble.utl` end with `50, 49, 34, 52, 51`. The parsed map keeps the file order, so the fixture round-trips byte for byte. Test: `src/core/format/profile.test.ts`, "reads the real block of BuffedLongBuffedDouble.utl" and "round-trips BuffedLongBuffedDouble.utl with its block parsed".
- [Verified] A block with an unknown type id keeps its body as raw text and round-trips. A `SalvageCombine` block that ends before the value mode section reads an empty value mode map. Its save adds the `0` count line, as the C# writer does. Test: `src/core/format/profile.test.ts`, "keeps a block with an unknown type id as raw data" and "reads an old block that ends before the value mode section".
